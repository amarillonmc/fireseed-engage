# 《メガミエンゲイジ》技能机制分类与移植规范

本文件是 `doc/me_skills.md` 的机制级整理，也是本项目技能接口、后台组合器与安装种子的共同语义基线。资料快照共 470 个技能；本文件只归纳“技能怎样工作”，不把同一机制的高数值换名版本误当成新机制。每张来源技能的复合机制、生命周期、数值依赖、用途域和迁移状态另在 `doc/me_skill_per_skill_mechanism_matrix.md` 按原顺序逐条记录。

## 1. 结论与边界

技能应拆成四个彼此独立的部分：

1. **发动生命周期**：常驻、立即执行、明确持续时间、下一次出征、出征快照或事件触发。
2. **效果机制**：攻击、速度、训练时间、立即获得资源等可复用动作。
3. **作用域与条件**：全军、兵种、资源、攻守方、目标类型、距离等。
4. **数值描述**：固定值、十级曲线、COST 曲线、智力曲线或 COST 与智力的仿射和。

同一技能可含多个 `effects`。例如“攻击 + 移速 + 返程速度”只是三个已登记机制的组合；上位技能只替换名称、等级曲线与冷却曲线，不增加 PHP 分支。

本轮接口承诺是：**管理员可任意组合注册表中标记为“已实现”的机制，无需再写代码**。它不等于允许数据库执行任意 PHP 方法，也不意味着尚无游戏状态或事件钩子的机制会被假装执行。未知机制、占位机制、非法参数和畸形曲线必须拒绝保存或在运行时 fail closed。

## 3. 状态定义

| 标记 | 含义 |
|---|---|
| **I — 已实现 / Implemented** | 当前项目已有权威状态和结算钩子；后台可直接组合。 |
| **A — 适配实现 / Adapted** | 当前项目可执行，但来源概念需显式映射到六资源、六元素或现有城池模型。 |
| **P — 占位 / Placeholder** | 已分类并登记名称，但当前设计缺少权威状态或事件；后台只能查看，不能启用。 |
| **M — 混合 / Mixed** | 分类内同时含 I/A/P 子机制，或基础数值机制已实现但来源技能的发动生命周期尚不能无损还原。 |

“已实现”描述的是机制接口，不代表 470 个来源技能都应原样安装。特别是来源资料没有给主动增益的持续时间，也没有明确说明普通主动战斗技能是不是“下一次出征消费”；这类来源行必须保留为待确认迁移，不能把 CT 当成持续时间。

### 5.2 已实现条件与作用域限制

| 条件 | 运算 | 用途 |
|---|---|---|
| `phase` | `eq`, `in` | 条件值全集为 `battle/march/return/production/training/construction/city_defense/scouting/activation`；每个机制只能选择其真实运行钩子会提供的子集。 |
| `side` | `eq`, `in` | `attack/defense`；避免防守加成在进攻预览中误算。 |
| `target_tag` | `eq`, `in`, `not_in` | `player/npc/city/army/tile/structure`，可表达 NPC 目标和建筑目标。 |
| `distance` | `lt/lte/eq/gte/gt` | 可表达 `聖白の天使` 的距离不超过 10。距离必须在出征时快照。 |

条件不是所有机制都能任意附加。注册表为每个已实现机制分别声明允许的条件类型、`phase` 值和 `side` 值；例如生产机制只接受 `phase=production`，返程速度只接受 `phase=return`，立即动作不接受战斗距离条件。后台只展示该机制可消费的组合，中央校验器也会拒绝数据库中手工写入但运行时没有对应上下文的条件，避免出现“能保存却永不生效”的配置。

#### `city_resource_production_percent` 的区间结算语义

城内资源生产不能用“结算瞬间的当前技能”回算此前全部经过时间，否则玩家可在结算前临时装备上位技能，或由管理员把共享卡片参数调高，使整段历史区间获得并不存在的加成。实现因此为每名玩家保存独立于资源余额 `last_update` 的生产游标、首个变化相对游标的偏移、最近变化/观察边界、未结算变化次数、独立的计划变化状态，以及按资源和 `facility_id` 稳定排序的逐设施单 tick v2 快照；每条设施流同时保存最终率 `per_tick` 与不含技能的 `base_per_tick`：

- 生产游标是所有 3 秒 tick 的固定锚点，只推进已经完整结束的 tick；不足一个 tick 的余数原样留待下次结算，状态变化不能把游标直接跳到当前时刻。
- 武将分配、HP/启用状态/生产相关属性、技能等级或效果、技能卡映射、后台共享卡定义、城池归属、设施状态发生变化时，19 个单语句触发器保存首边界偏移、覆盖最近边界、饱和累加 `change_count`，并使已固定的多变化窗口失效。城池和设施结构变化从一开始就按至少两次变化保守标记，避免“建立/转移时尚未生效，结算时已经完成”的单端点追授。
- `change_count=1` 时仍精确使用旧、新端点：边界前及跨越边界的 tick 使用旧快照，当前快照从下一完整 tick 起使用。tick 始终按起点归属，因此一次真实变化既不丢 tick，也不会把新技能追溯到变化之前；一次且仅一次的无关变化若两端快照相同，则可安全连续使用旧快照。
- `change_count>1` 时不能从相同端点推断中途状态。旧快照只结算到首边界；从首边界后的下一 tick 到本次首次观察边界，只支付两端同一 `facility_id`、同一资源且 `base_per_tick` 完全相同的共同基础率，当前最终率在观察边界的跨界 tick 完整结束后才接管。这样 `high→low→high`、`low→high→low` 和多次无关变更都不能绕过计数追授技能加成，同时未变化设施的正常基础产出不归零；升级前后 base 不同、新增、删除或改色的设施在不确定区段不支付。若跨界 tick 尚未结束，观察边界会固定；之后任何触发器变化都会使其失效，并在下一次结算时把保守窗口延伸到新的观察时刻。
- 设施建造或升级的未来完成时间不再复用 `dirty_at`，而以相对生产游标的计划偏移和已知计划变化数独立保存。所有当前已知未来转换都会计数；计划到期时与实际 `change_count` 合并，所以“先有未来完成时间、再发生普通变化、最后一起结算”至少形成多变化窗口，普通变化不能覆盖并提前追授设施。普通资源获得、消费和后台余额调整只改变余额及兼容字段 `last_update`，不会推进、重置或弄脏独立生产状态。
- 若运行时发现没有实际或到期计划记录的意外快照变化，则以当前时刻作为一次边界，旧快照结算到当前完整 tick，新快照只供后续 tick 使用。v1 快照没有可信 `base_per_tick`，升级后会安全失效并只建立当前 v2 基线，不追授历史；迁移用 `information_schema` 与仓库内置 `PREPARE` 流程为已运行上一版脚本的服务器可重跑补列。
- 赛季冻结同步平移 `settled_at` 与实际/观察 `dirty_at`；首边界和计划边界都保存为相对游标偏移，因此随 `settled_at` 自动等量平移而无需改写，冻结期间仍不生产。

另有几个应保持为占位语义而不能偷偷降级的横切能力：

- **同据点全卡光环**：`全員でどーん!`、`皆でびゅーん!`。
- **从开发/来源据点出发**：`戦陣の踊り`、`美姫の我儘`。
- **角色与オートマタ采用不同系数**：`××料理娘`、`天賦の才能`。当前军队模型没有“武将本人战力”和“士兵战力”的独立加区。
- **按同驻城智力、角色防御或速度二次修正**：`文殊の知恵`、`衛士の誓約`、`瞬秒の嚆矢`，且来源缺少修正系数。
- **不叠加/仅取最强**：`守護の光` 明示同技能不重叠；在统一 stacking 接口落地前不能按普通相加处理。
- **下一次出征消费**：来源普通主动战斗技能很可能属于此类，但资料没有明确字段，当前也没有可消费的效果实例。

## 6. v2 数据接口

结构化定义的最小形式如下：

```json
{
  "schema_version": 2,
  "application_mode": "continuous",
  "effects": [
    {
      "mechanism": "army_stat_percent",
      "parameters": {
        "stat": "attack",
        "unit_type": "rook"
      },
      "value": {
        "mode": "cost_level_values",
        "values": [7, 9, 11, 13, 16, 19, 22, 26, 30, 35]
      },
      "conditions": [
        {
          "type": "distance",
          "operator": "lte",
          "value": 10
        }
      ]
    },
    {
      "mechanism": "army_return_speed_percent",
      "parameters": {},
      "value": {
        "mode": "level_values",
        "values": [10, 12, 14, 16, 18, 20, 23, 26, 30, 35]
      },
      "conditions": []
    }
  ]
}
```

后台新增技能只需要选择发动模式、增加任意多个效果块、选择机制及参数、输入与 `max_level` 等长的等级曲线和可选条件。原作直接移植时 `max_level=10`，因此使用十级曲线。注册表决定允许的参数、数值上下限、主动/被动兼容性和是否可执行；运行时与后台必须调用同一个校验器。

旧平面 JSON 只作为已有数据兼容层存在。新技能应使用 `schema_version: 2`，不得用未知键猜测运行行为，不得用 `eval`，也不得从数据库指定 PHP 类名或方法名。

## 7. 数值公式

### 7.1 支持的值描述

| `mode` | 公式 |
|---|---|
| `fixed` | 固定值 |
| `level_values` | `values[level - 1]` |
| `cost_level_values` | `general_cost × values[level - 1]` |
| `intelligence_level_values` | `general_intelligence × values[level - 1]` |
| `cost_intelligence_level_values` | `general_cost × general_intelligence × values[level - 1]`；只用于资料明确为乘积的设计 |
| `cost_plus_intelligence_level_values` | `general_cost × cost_term[level] + general_intelligence × intelligence_term[level] + constant_term[level]` |
| `stat_level_values` | 指定武将属性 × `values[level - 1]` |

### 7.2 `COST*a + 智力*b` 的关键判读

来源文本形如：

```text
(コスト*11知力*0.25)%
```

不得解析成 `COST × 11 × 智力 × 0.25`。结合来源 COST 列可知它是两个贡献项的和：

```text
最终值 = COST × 11 + 智力 × 0.25
```

因此应记录为：

```json
{
  "mode": "cost_plus_intelligence_level_values",
  "values": [
    {"cost": 11, "intelligence": 0.25, "constant": 0}
  ]
}
```

每一级分别保存 `cost`、`intelligence` 和可选 `constant`，不能只保存 Lv1 再用项目自创倍率外推。

### 7.3 曲线规则

- 来源技能都是 10 级；直接移植时数值曲线和 CT 曲线必须各有 10 项。
- 新技能可使用目录声明的 `max_level`，但所有等级曲线长度必须与之相同。
- 只接受有限数值；拒绝 `NaN`、无限值、数字字符串、超出机制上限的值和未知字段。
- `cooldown` 与 `duration` 的 COST、智力或属性曲线在求值后仍强制封顶为 31,536,000 秒，不能用合法系数乘出超长生命周期。
- 百分比、固定伤害与倍率是不同单位，不能共用一个模糊 `value` 语义。
- 多效果技能逐条解析并原子校验；任一条无效则整张技能不可启用。

## 8. CT 与发动生命周期

### 8.1 CT 的迁移决定

来源只给出形如 `60:00`、`72:00` 的 CT，没有在文件内声明单位。由于存在大于 59 的首段，本项目迁移时暂按 **小时:分钟（H:MM）** 解析，并在导入说明中标为“来源推定”。例如 `60:00` 暂换算为 `216000` 秒。若以后取得权威资料，只需要修订冷却曲线，不改变效果机制。

`00:00` 结合“自動発動”视为常驻。多行 COST 单元格可能换行；每级行的**最后一个 CT 列**才是冷却值。

### 8.2 CT 绝不等于 duration

CT 是再次发动前的等待时间；duration 是效果保持多久。`me_skills.md` 没有提供主动增益的 duration。以下处理是强制规则：

| `application_mode` | 含义 | 来源迁移规则 |
|---|---|---|
| `continuous` | 常驻被动 | `00:00` 且自動発動的技能可直接移植。 |
| `instant` | 发动时立即执行 | 立即资源、治疗、修复、冷却缩短可直接执行，然后进入 CT。 |
| `timed` | 明确持续若干秒 | 后台必须另填 `duration`；来源仅写“スキル発動中”而没有时长时不得猜。 |
| `next_dispatch` | 下一次出征消费 | 当前只分类占位；需要可消费效果实例。 |
| `dispatch_snapshot` | 出征时固化到该次行军/战斗 | 当前只用于内部快照，不作为管理员随意伪造的来源字段。 |
| `event` | 战斗成功、牵制、援军到达等事件触发 | 对应事件不存在时为 P。 |

普通非零 CT 战斗技能既不是 instant，也不能仅凭 CT 证明是 timed。它们的攻击/速度机制本身已经可组合，但原作整张技能暂不作为安装基础数据，直到 `next_dispatch` 生命周期得到权威确认和实现。
